## 1. Can you tell me how you use GitHub in your projects?
I primarily use GitHub for source-code management and collaboration. Developers push their code to feature branches, and we create pull requests for code review. Once the PR is approved and merged into the main branch, it triggers our CI pipeline through a webhook. In my DevOps projects, GitHub is basically the starting point of the CI/CD process

### 2. What's the difference between Git and GitHub?
Git is a distributed version control system that runs locally and tracks changes in source code. GitHub is a cloud-based platform that hosts Git repositories and provides collaboration features like pull requests, code reviews, branch protection, issues, and CI/CD integration.

### 3. Can I use Git without GitHub?
Yes. Git doesn't depend on GitHub. I can use Git locally and connect it to other remote repositories such as GitLab, Bitbucket, or even a self-hosted Git server.

### 4. Walk me through your Git workflow.
First, I would pull the latest code from the main branch. Then I would create a feature branch and work on the changes. After testing locally, I would commit and push the branch to GitHub. Then I would create a pull request. The PR goes through code review and automated checks. Once it's approved and all checks pass, it's merged into the main branch, which then triggers the CI/CD pipeline.

### 5. Why do you create branches?
I create branches primarily for risk isolation and seamless collaboration.

If we make changes directly on main, we risk pushing broken code straight to production, which directly impacts users and disrupts the team.By using feature branches, I can develop, test, and run automated CI/CD pipelines in a safe environment.
It also allows for code reviews through Pull Requests, ensuring that at least one other set of eyes verifies the code before it ever touches our stable production environment."

### 6. What is a Pull Request?
A pull request is a request to merge changes from one branch into another, usually a feature branch into main. Other developers can review the changes, add comments, and approve or request changes. Automated CI checks can also run against the PR. We merge it only when the required reviews and checks are successful

### 7. What are branch protection rules? or How would you protect your main branch?
I would enable branch protection rules. For example, I can prevent direct pushes, require pull requests, require one or more approvals, and require CI status checks to pass before merging. This helps prevent untested or unauthorized code from reaching the main branch.

### 8. What is a merge conflict?
A merge conflict happens when Git cannot automatically merge code because two people changed the same line of code in the same file, or one person edited a file while another deleted it. Git gets confused about which version to keep and pauses the merge, requiring human intervention.

### 9. What are the steps to resolve it?

- To resolve it, I run `git status` to locate the affected files, open them in my editor, and look for the conflict markers.

- I then collaborate with the teammate who wrote the competing code if needed, clean up the file to keep the correct logic, and delete the Git markers. 

- Finally, I stage the resolved file with `git add` and `commit` the merge to finish the process." then push it.

#### Rebase Conflicts

- When resolving conflicts during a git rebase, the process is slightly different because Git applies your changes commit-by-commit.
- After fixing the conflict markers in the code, I stage the changes using `git add`. 
- However, instead of making a new commit, I run `git rebase --continue`. 
- Git will then apply the next commit. Once the entire rebase is successful, I use `git push --force-with-lease` to safely update the remote tracking branch, since rebasing rewrites the commit history.

### 10. merge vs rebase

"I choose between merge and rebase based on **history management and team workflow**.

I use **git merge** when I want to preserve the exact historical timeline of the project, as it creates a dedicated merge commit showing exactly where branches joined. It's also the safest option for public or shared branches.

I use **git rebase** on my local, private feature branches to pull in updates from main. It rewrites the base of my branch so my changes sit cleanly on top of the latest production code, creating a perfectly linear history that makes debugging and reading logs much easier."

|Feature|git merge|git rebase|
|-------|---------|----------|
|History |StructureNon-linear (shows branches and joins)|Linear (one straight line of commits)|
|Commit History | Preserves original timestamps and logs | Rewrites history (creates new commit hashes) |

### 11 . Would you rebase a shared branch?
Generally, no. Rebase rewrites commit history, so doing it on a branch that other developers are already using can cause problems. I would typically rebase my own feature branch before merging.

### 12. git pull vs git fetch?
When I run **git fetch**, Git downloads the latest changes from the remote repository into my tracking branches, but it doesn't touch my working files. This allows me to use git log or git diff to review what my team has changed before I bring it into my code.

**git pull**, on the other hand, is a combination of git fetch and git merge. It downloads the changes and immediately attempts to combine them with my local branch. I often prefer using git pull --rebase in my daily workflow to keep our project history clean and linear.

### 13. What happens when you do git push?

When I run git push, Git uploads my local commits, file changes, and branch history to the remote repository, like GitHub.

Before the transfer happens, Git ensures that my local branch is fully synced with the remote branch. If the remote branch has new commits from other developers that I don't have yet, Git will safely reject my push. This forces me to pull and resolve any conflicts locally first. Once verified, it transfers the data and updates the remote tracking pointers, which often kicks off our automated CI/CD testing pipelines.

### 14. A developer says git push is rejected. What do you check?
First I'd look at the exact error message. If it's a non-fast-forward error, I'd check whether someone pushed new changes to the remote branch. I would fetch the latest changes and then merge or rebase them before pushing again. 

If it's a permission error, I'd check repository permissions and authentication. If it's the main branch, I'd also check whether branch protection is preventing the push.

### 15. Revert vs reset
I would generally use **git revert** because it creates a new commit that reverses the changes from the bad commit. This is safer for a shared branch because it doesn't rewrite the existing history.

**Reset** changes the branch history, which can cause problems if the commits have already been pushed and other developers are working on them. So for a shared branch like main, revert is usually safer.

The Three Flavours of git **reset**

- `--soft:` Moves the history back, but keeps your changes staged (in the green zone). Ready to be recommitted.
- `--mixed (Default)`: Moves the history back, keeps your changes, but unstages them (in the red zone).
- `--hard:` Moves the history back and completely deletes all changes. Your working directory is wiped clean to that exact moment in time.

### 17. Someone committed a password to GitHub. What do you do?

First, I wouldn't assume that deleting the commit solves the problem. 
I would immediately revoke or rotate the exposed AWS credentials. 
Then I'd check CloudTrail for any suspicious activity.
After that, I'd remove the secret from the repository history if necessary and make sure the secret is stored securely, such as in GitHub Secrets or AWS Secrets Manager.
Finally, I'd add the sensitive file to `.gitignore` and enable appropriate secret scanning and prevention controls.

### 18. How do you store secrets in GitHub?

I would never hardcode credentials in the repository or workflow file. For GitHub Actions, I can use GitHub encrypted secrets. For AWS authentication, I would prefer OIDC with an IAM role because it avoids storing long-lived AWS access keys.

### 19. Cherrypick

git cherry-pick is a powerful command used to apply a specific commit from one branch onto another branch, without merging the entire history.A common scenario where I use this is for critical hotfixes. If I resolve a production bug inside a broader development branch, I don't want to merge the whole branch because it contains unfinished features. Instead, I find the commit hash of that specific bug fix, switch over to the release or main branch, and run git cherry-pick [hash]. This copies just that isolated fix exactly where it's needed, keeping our production environment stable and clean.

### 20. git reflog

`git reflog` is my absolute safety net. Unlike git log which only tracks the current branch's commit history, reflog tracks every single action my local HEAD pointer takes. If a developer accidentally runs a destructive command like `git reset --hard` or mismanages a complex rebase, `git reflog` allows us to look at the history of our actions, locate the lost commit hash, and cleanly restore the codebase back to its exact state before the mistake.

### 21. git switch vs checkout 

" `git switch` was introduced to separate concerns from the older git checkout command. `git checkout` is a dual-purpose tool used for both navigating between branches and modifying individual files, which can sometimes lead to accidental file overrides. `git switch` is a modern, safer command dedicated strictly to switching or creating branches, making the intent of the command much more explicit."

### 22. delete a branch

To delete a branch locally, I use `git branch -d`, which is safe because Git will warn me and block the deletion if the changes haven't been fully merged yet. If I'm intentionally discarding an experimental branch, I force it using a capital -D. To clean up the shared remote repository after a Pull Request is closed, I delete the remote copy by running `git push origin --delete`.

### 23. describe commit
To review project history, my go-to command is git log. For a quick and comprehensive view of how branches have split and merged, I use git log --oneline --graph --decorate. This gives me a highly readable, linear layout of the entire repository history. If I need to audit a specific bug or review what changed in a file over time, I filter the logs using commands like git log -p or target the specific file directly using git log -- [filename].

### 24. What is GitHub Actions?

GitHub Actions is GitHub's CI/CD automation platform. We define workflows using YAML files under .github/workflows. Workflows can be triggered by events such as push, pull request, or manual execution. Inside a workflow, we define jobs and steps that can perform tasks such as testing, code scanning, building Docker images, pushing them to ECR, and deploying applications.

### 25. What's a runner in GitHub Actions?

A runner is the machine that actually executes the jobs in a GitHub Actions workflow. We can use GitHub-hosted runners, or we can configure our own self-hosted runner when we need more control over the environment.

### 26. Your GitHub Actions pipeline is failing. What do you do? or The pipeline was working yesterday, but today it's failing. How do you troubleshoot?

I would first open the workflow logs and identify the exact stage and command that failed. Then I'd check whether there were recent code, dependency, workflow, or infrastructure changes. If the failure involves authentication, I'd check the secrets or OIDC/IAM configuration. If it's a Docker build failure, I'd check the Dockerfile and build context. I would reproduce the issue locally where possible and then fix the root cause rather than just rerunning the pipeline.

### 27. GitHub → Jenkins. How does it work?

We configure a GitHub webhook pointing to Jenkins. When an event such as a push occurs, GitHub sends an HTTP request to Jenkins. Jenkins receives the webhook and triggers the configured pipeline. The pipeline then checks out the code and starts the required CI stages.

### 28. Jenkins isn't triggered after a GitHub push. Troubleshoot it.

First, I'd check the GitHub webhook delivery status to see whether GitHub successfully sent the request. Then I'd check Jenkins logs and webhook configuration. I'd verify that the repository URL and branch configuration are correct and that Jenkins is reachable from GitHub. I'd also check whether the Jenkins job is configured to trigger from the expected GitHub event.

### 29. How would you implement CI/CD using GitHub?

1. For example, when a developer pushes code, GitHub triggers Jenkins through a webhook. 
2. Jenkins checks out the code and performs code-quality analysis using SonarQube, security scanning using Trivy, and builds the Docker image. 
3. The image is then pushed to Amazon ECR. 
4. For deployment, instead of Jenkins directly modifying Kubernetes, we can update the GitOps repository and let Argo CD synchronize the changes to EKS.

We separate application source code from deployment configuration. The application repository contains the source code and CI configuration, while the GitOps repository contains Kubernetes manifests or Helm configuration. ### 31. What if someone directly changes Kubernetes?
or
### Suppose someone manually changes a deployment using kubectl. What happens?

In a GitOps model, that change creates drift because the live cluster state differs from the desired state in Git. Argo CD can detect that drift and, depending on the sync configuration, reconcile the cluster back to the state defined in Git.

### 32. How would you rollback?"

If we're using GitOps, I would revert the deployment change in the GitOps repository to the previous known-good version. Argo CD would detect the Git change and synchronize the previous version back to the cluster. I would also investigate why the deployment failed before redeploying the newer version.

### 35. What is branch?
"In Git, a branch is fundamentally just a lightweight pointer to a specific commit. It represents an isolated timeline of development.Instead of making changes directly to the production code, creating a branch allows me to build features, fix bugs, or experiment safely in isolation. Once the work on that branch is complete, tested, and reviewed, we can merge that pointer's history back into the main branch. This keeps our production environment stable while allowing multiple developers to work on the codebase simultaneously without stepping on each other's toes."

### 36. How do you recover a deleted branch?
Recovering a deleted branch depends on whether it was a local or remote deletion.

If a branch is deleted locally, Git doesn't immediately delete the underlying commits; it just removes the pointer. I would run git reflog to trace the movement of my local HEAD pointer, locate the exact commit hash where the branch was standing right before deletion, and then run git checkout -b [branch-name] [commit-hash] to recreate it.

If the branch was remote and deleted on GitHub after closing a Pull Request, I would simply navigate to the closed PR page and click the 'Restore branch' button.

### 37. What is a detached HEAD? How would you find which commit introduced a bug? When would you avoid rebasing a shared branch? How would you find which commit introduced a bug? 
A detached HEAD happens when Git's HEAD pointer looks directly at a specific commit hash instead of a branch pointer. Any changes made here aren't saved to a branch timeline. To fix it and save my work, I just run git switch -c [new-branch-name].

When I need to find which commit introduced a bug, my absolute best tool is git bisect. It uses a binary search algorithm across the project history. I mark a known 'good' commit from the past and a 'bad' commit from the present. Git automatically checks out the midpoint commit, and I flag it as good or bad. It cuts down the debugging time exponentially compared to manual checking.

Finally, the golden rule of rebasing is to never do it on a shared public branch. Because rebasing rewrites commit hashes, force-pushing a rebased shared branch destroys the timeline integrity for the rest of the team, leading to terrible sync issues and duplicate commits for my teammates.

### 38.what is forking? or How to keep a Fork updated

Forking is the process of creating a complete, independent copy of an existing repository under your own remote account on a platform like GitHub.It is most commonly used in open-source development. Because external developers don't have write access to a main project repository, they fork it to their own profile, implement features or bug fixes safely in their copy, and then submit a Pull Request to propose those changes back to the original project owners. It differs from a standard branch because a branch lives inside the same ecosystem, whereas a fork is a completely separate repository copy

```bash
# 1. Add the original project as a remote named 'upstream'
git remote add upstream https://github.com

# 2. Fetch the latest changes from the original project
git fetch upstream

# 3. Merge those changes into your local main branch
git checkout main
git merge upstream/main
```
